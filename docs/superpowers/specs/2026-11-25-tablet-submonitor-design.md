# 갤럭시탭 USB 서브모니터 설계

작성일: 2026-11-25

## 의도와 배경

갤럭시탭 S8 Ultra를 USB로 연결해 PC의 **확장 모니터**로 쓰는 개인용 도구.
최종적으로는 macOS와 Windows 양쪽에서 쓰려 하지만, **1차 버전은 이 맥북(macOS)만** 대상으로 한다.

Windows에서 삼성 세컨드 스크린(Miracast, 무선)을 써 봤지만, 커서를 움직이거나 브라우저를 띄워 놓고
간단한 작업을 할 때도 지연이 커서 쓸 수 없다고 판정했다. 이 도구는 그 지연을 없애는 것이 존재 이유다.

주 용도: 탭에 브라우저 등을 띄워 놓고 **PC의 마우스·키보드로** 작업한다. 탭에 펜으로 그리는 용도가 아니다.

## 목표 (1차)

- 이 맥북(macOS 27, Apple Silicon)에서 탭이 실제 모니터로 인식된다(확장 모드, 창을 끌어다 놓을 수 있음).
- 커서를 서브모니터 위에서 움직일 때 즉각 반응한다고 느껴진다.
- 스크롤·타이핑 등 브라우저 작업의 화면 반영이 느리다고 느껴지지 않는다.
- 브라우저 글자가 선명하게 읽힌다.
- 주사율은 120Hz를 노리되 60Hz도 허용한다. 커서는 탭이 직접 그리므로 영상이 60fps여도 커서는 120Hz로 움직인다.
- Android 앱과 탭으로 보내는 데이터 형식은 나중에 Windows 호스트에서도 그대로 쓸 수 있게 한다.

## 비목표 (1차)

- Windows 호스트 구현
- 탭의 터치·S Pen 입력을 PC로 보내기
- 무선 연결
- 갤럭시탭 S8 Ultra 외 기기 지원, 여러 대 동시 연결
- 외부 배포(서명, 앱 스토어, 설치 패키지)
- 오디오 전송

## 실패 기준 (동작은 해도 실패로 보는 것)

- 체감 지연이 세컨드 스크린(100ms 이상)과 비슷하다.
- 브라우저 글자가 뭉개져서 읽기 불편하다.

## 제약

- 대상 기기: 갤럭시탭 S8 Ultra
  - 해상도 2960×1848, 120Hz, Snapdragon 8 Gen 1, USB-C 3.2 Gen 1
- 연결: USB만. 탭의 USB 디버깅을 켜는 것은 허용(개인용).
- 개인용이므로 macOS 비공개 API 사용을 허용한다.
- 지연은 구조적으로 실제 모니터(약 5~15ms) 수준까지는 못 줄인다. 합격 기준은 '검증 계획' 참조.
- 개발 환경(확인됨): ffmpeg(Homebrew), adb, Android SDK(build-tools 35/36, platform android-36), OpenJDK 21, Swift.
  Gradle과 Android Studio는 설치되어 있지 않다.

## 검토한 방안

| 방안 | 내용 | 판단 |
|---|---|---|
| A. 기성품 | Windows는 SuperDisplay·spacedesk(USB 지원), mac+Android+USB는 Duet(유료 구독) 정도 | OS마다 다른 도구, 지연·화질 제어 불가 |
| **B. FFmpeg 얇은 호스트 + Android 앱** | 캡처·인코딩은 FFmpeg, 호스트는 가상 디스플레이·커서·연결 관리, 탭은 전용 앱 | **채택** |
| C. 완전 네이티브 호스트 | ScreenCaptureKit + VideoToolbox 직접 구현 | 지연 최저, 코드량 몇 배. B에서 병목이 확인되면 이행 |

B를 고른 이유: 가장 위험한 부분(가상 디스플레이, 지연 수준)을 가장 적은 코드로 검증할 수 있다.
B와 C는 탭으로 보내는 데이터(압축 영상 + 커서 메시지)가 같으므로, 호스트를 C로 바꿔도 Android 앱은 그대로 쓴다.

검토 후 버린 것:
- 브라우저 클라이언트: 여러 기기 지원이 장점이었는데 탭이 하나로 고정되어 이점이 없다. 지연도 더 크다.
- USB 테더링: mac이 삼성 테더링 방식(RNDIS)을 기본 지원하지 않는다.
- AOA(Android Open Accessory): Windows에 별도 USB 드라이버(WinUSB) 설치가 필요하다.

## 구조

```
[mac 호스트]                                              [갤럭시탭 앱]
가상 디스플레이 ─→ FFmpeg (커서 제외 캡처 + HEVC 인코딩) ─┐
                                                          ├─ adb reverse (USB, TCP) ─→ 디코딩 → 즉시 표시
커서 좌표·모양 수집 ──────────────────────────────────────┘                           → 커서 직접 그림
```

### 1. 가상 디스플레이

- `CGVirtualDisplay`(비공개 API). DeskPad, BetterDisplay가 쓰는 방식이다.
- 2960×1848 물리 해상도, HiDPI(논리 1480×924), 120Hz로 만든다.
- 호스트 프로세스가 살아 있는 동안만 디스플레이가 유지되고, 종료하면 사라진다.

### 2. 캡처와 인코딩 (FFmpeg)

- `avfoundation` 입력(`-capture_cursor 0`) + `hevc_videotoolbox`
- 설정 방향: B-프레임 없음, 저지연 모드, 키프레임 간격 길게, USB 대역폭을 활용한 넉넉한 비트레이트
- 코덱은 HEVC 우선. 2960×1848@120은 H.264 레벨 5.2 한계를 넘으므로, H.264는 60Hz 대안으로만 둔다.

### 3. 커서 분리 (체감 지연의 핵심)

- 캡처 영상에서 커서를 빼고, 호스트가 커서 좌표와 모양을 별도 채널로 보낸다.
- 탭 앱이 영상 위에 커서를 직접 그린다. 압축·해제를 거치지 않으므로 커서는 몇 ms 수준으로 따라온다.
- 커서가 가상 디스플레이 밖에 있으면 탭에서 숨긴다.
- 모양: 브라우저에서 바뀌는 화살표·텍스트 커서·손가락 등을 반영해야 한다(이미지 + 핫스팟).
- 알려진 한계: 커서는 즉각 움직이지만, 호버 효과·클릭 결과 등 화면 내용은 영상 지연만큼 늦다.

### 4. 전송

- `adb reverse tcp:<포트> tcp:<포트>`로 탭의 localhost 연결을 호스트로 넘긴다.
- 영상과 커서는 서로 다른 TCP 연결로 보낸다(커서 메시지가 영상 데이터 뒤에 줄 서지 않게).

### 5. 탭 앱 (Android)

- `MediaCodec` 하드웨어 디코딩, `KEY_LOW_LATENCY` 사용, `SurfaceView`에 직접 출력
- 디코딩된 프레임은 쌓지 않고 즉시 표시(최신 프레임만 유지)
- 화면 주사율 120Hz를 명시적으로 요청(삼성 적응형 주사율이 60Hz로 내려가지 않게)
- 전체 화면, 화면 꺼짐 방지
- 커서 오버레이 레이어

### 6. 실행 흐름

호스트 명령 하나로 다음을 수행한다:
1. 가상 디스플레이 생성
2. 탭 앱이 없으면 `adb install`, `adb reverse` 설정
3. 탭 앱 실행(`adb shell am start`)
4. FFmpeg와 커서 전송 시작
5. 종료 시 정리(FFmpeg 종료, 가상 디스플레이 제거)

## 결정 사항

사용자가 정한 것:
- 개인용, 갤럭시탭 S8 Ultra 전용, USB 전용
- 주 용도는 PC 마우스·키보드로 하는 브라우저·일반 작업
- 1차 버전은 이 맥북만 대상, Windows는 구현하지 않음
- 1차 버전에서 터치·S Pen 입력 제외

제안했고 사용자가 이의를 제기하지 않은 것:
- B 방안 채택
- 커서 분리

설계자 판단:
- 호스트: Swift 단일 실행 파일. 비공개 API(`CGVirtualDisplay`)와 커서 API를 직접 쓰고, FFmpeg·adb는 하위 프로세스로 실행한다.
  (앞서 양쪽 OS 공통을 위해 Python을 제안했으나, 1차가 mac 전용이 되어 언어를 하나로 줄였다. C로 이행할 때도 그대로 이어진다.)
- 탭 앱: Kotlin. Gradle은 래퍼 방식으로 저장소에 포함한다.
- 코덱: HEVC 우선
- 120Hz는 필수가 아니다. 막히면 60Hz로 낮추는 것이 첫 대안이다.
- 이번 구현 계획의 범위는 B안과 지연 측정까지다. C안은 측정 결과로 필요할 때 별도 계획으로 세운다.

## 검증 계획

첫 단계는 가장 위험한 부분을 확인하는 시험이다.
- macOS 27에서 `CGVirtualDisplay`로 2960×1848 HiDPI 120Hz 디스플레이가 만들어지는가
- FFmpeg `avfoundation`(구형 API)으로 그 디스플레이를 캡처할 수 있는가. 120fps가 안 되면 60Hz로 낮춘다.
  캡처 자체가 안 될 때만 C로 이행한다(ScreenCaptureKit).
- S8 Ultra 디코더가 2960×1848@120 HEVC를 버티는가. 못 버티면 60Hz로 낮추고, 그래도 안 되면 해상도를 낮춘다.

탭을 USB 디버깅 상태로 연결해 두면 구현자가 직접 확인할 수 있는 것:
- APK 설치·실행, 로그(`adb logcat`), 탭 화면 캡처(`adb exec-out screencap`)로 표시 결과 확인
- 디스플레이 주사율·디코더 성능 조회

사용자가 확인해야 하는 것:
- 지연 측정(카메라 촬영)과 실제 사용 체감

지연 측정 방법:
- 가상 디스플레이를 주 화면의 복제(미러링)로 두고 ms 스톱워치를 띄운다.
- 두 화면을 휴대폰 카메라로 함께 촬영해 시간 차이를 읽는다.
- 비교 기준: 같은 방법으로 잰 세컨드 스크린 수치

합격 기준:
- 최종 판정은 사용자가 실제 브라우저 작업(커서 이동, 스크롤, 타이핑)에서 느리다고 느끼지 않는 것이다.
- 측정값은 참고용이다. 목표치(설계자 제안)는 화면 내용 40ms 이하, 커서는 체감상 즉각이다.
- 불합격이면 단계별(캡처·인코딩·전송·디코딩·표시) 시간을 재서 병목 단계만 교체한다.

## 구현자 재량

- 영상 프레임 경계 처리 방식(AUD 삽입 또는 길이 헤더 등)
- 포트 번호, 커서 메시지 형식
- FFmpeg 세부 튜닝 값
- 가상 디스플레이와 FFmpeg `avfoundation` 화면 번호의 대응 방법
- 저장소 디렉터리 구조

## 향후 Windows 참고 (이번 범위 아님)

- 대상 PC: NVIDIA + Intel GPU, Windows 11. 지금은 테스트 불가.
- 가상 디스플레이: 서명된 오픈소스 간접 디스플레이 드라이버(예: VirtualDrivers/Virtual-Display-Driver), 2960×1848@120Hz, 배율 200%
- 캡처·인코딩: FFmpeg `ddagrab`(`draw_mouse=0`) + `hevc_nvenc` 또는 `hevc_qsv`
- 주의: GPU가 두 개라 가상 디스플레이를 그리는 GPU, 캡처하는 GPU, 인코딩하는 GPU를 하나로 맞춰야 할 수 있다.
- 탭을 쓰지 않을 때 가상 모니터가 남아 있으면 커서·창이 보이지 않는 화면으로 넘어간다. 호스트 실행 중에만 켠다.
- Android 앱과 전송 형식은 그대로 재사용한다.
